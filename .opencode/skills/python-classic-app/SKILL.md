# Python App Layer in "Classic" Architecture

## Описание

В этом навыке описывается слой приложения (app) - нижний, основной слой.
Общая идея слоёв описана в навыке `python-classic-architecture`.
Слой app может содержать опциональную модель домена, она описана в навыке `python-classic-domain`.

## Когда использовать
- Во время разработки новых команд и запросов.
- Во время ревью бизнес-логики.
- При написании тестов на usecase.

## Структура
Раскладка пакета `app/` - в разделе Layout навыка `python-classic-architecture`.

## Общие правила
- Содержит в себе логику, обеспечивающую потребности бизнеса.
- Не должен содержать обращения к инфраструктуре и другим системам. Вместо прямых обращений приложение должно объявлять абстрактный базовый класс и использовать его. Реализации абстрактного класса выносятся на слой адаптеров, а в usecase попадают через конструктор.
- Запрещено импортировать в app драйверы БД, `classic.db_tools.Engine`, веб-фреймворки, библиотеки парсинга и сериализации и SQL: любая такая зависимость привязывает бизнес-логику к конкретной технологии - её нельзя будет тестировать in-memory и переносить без переписывания. DTO слоя app - чистые датаклассы стандартной библиотеки.
- Каждое действие в приложении, возможное в системе, должно быть выражено как usecase - класс с публичным методом run. Это даёт единообразие: любое действие находится и вызывается одинаково, классы usecase - явный список возможностей системы, а сквозную функциональность (транзакции, логирование) удобно навешивать на одинаковый интерфейс.
- Usecase делятся на команды (меняют состояние) и запросы (читают данные). Это CQRS: команды и запросы живут в разных пакетах и не зависят друг от друга.
- Если "usecase" сводится к одному обращению к хранилищу без бизнес-логики, это не usecase, а адаптер: такой класс - посредник без ответственности, он только проксирует вызов и размывает границу между слоями. Приложение в этом случае объявляет ABC или испускает сигнал (см. Сигналы).
- К usecase не должно быть обращения из уровня приложения, только из адаптеров. Исключение - доменные usecase, которые вызываются из команд. Вызовы usecase из usecase связывают их и размывают границы операций: у каждого usecase своя транзакция, свои права, свой сценарий. Переиспользуемая логика при этом может выноситься в отдельные классы (не usecase) и вызываться из нескольких usecase - запрет касается именно вызовов usecase из usecase.
- Комментарии и docstring в app не ссылаются на реализации и файлы верхних слоёв: знание о верхних слоях не должно протекать в app даже через документацию, иначе контракт привязывается к конкретной реализации и вводит в заблуждение при её замене. Описание контракта говорит "что это значит", а не "кто это обрабатывает".

## Параметры и результат
- Параметры принимаются usecase в виде датаклассов или простых типов данных, их описание размещается в том же файле, что и usecase. Входные параметры называются `<UseCase>Params`.
- Датаклассы параметров НЕ переиспользуются между usecase и не выносятся в общий файл, даже если структуры совпадают: два usecase с похожими `PatternParams` содержат две независимые копии. Usecase эволюционируют независимо, а общий датакласс связал бы их: при изменении контракта одного usecase менялись бы другие, что особенно болезненно при одновременной поддержке нескольких версий приложения. Кода чуть больше, зато он развязан.
- Как получить `Params` из внешнего представления (HTTP-запроса, сообщения бота, задачи, сообщения очереди), решает адаптер, вызывающий usecase. Он разбирает данные и создаёт датакласс ДО вызова usecase. Поэтому usecase не проверяет структуру и типы данных.
- Все проверки корректности входных параметров выполняются в `__post_init__` датакласса `Params`, а не в `run`: диапазоны, пагинация (`limit` > 0 и не больше максимума, `offset` >= 0), согласованность полей. Так невалидный объект параметров невозможно создать, и `run` работает только с корректными данными.
  ```python
  @dataclass(frozen=True)
  class FindBooksParams:
      MAX_LIMIT: ClassVar[int] = 100
      MIN_SEARCH_LENGTH: ClassVar[int] = 3

      title__contains: str | None = None
      limit: int = 20
      offset: int = 0

      def __post_init__(self) -> None:
          if not 0 < self.limit <= self.MAX_LIMIT:
              raise ValueError(f'limit должен быть от 1 до {self.MAX_LIMIT}')
          if self.offset < 0:
              raise ValueError('offset не может быть отрицательным')
          search = self.title__contains
          if search is not None and len(search) < self.MIN_SEARCH_LENGTH:
              raise ValueError(f'Строка поиска короче {self.MIN_SEARCH_LENGTH} символов')
  ```
- `__post_init__` при нарушении бросает встроенный `ValueError` с понятным сообщением. Отдельные классы ошибок (`AppError`) под каждую проверку параметров не объявляются: некорректные параметры - это ошибка ввода, а не бизнес-ситуация, которую клиенту нужно различать по типу.
- Константы, нужные проверкам (максимумы, минимальные длины), объявляются `ClassVar` на классе параметров.
- `run` не повторяет проверки параметров: некорректные параметры не доходят до usecase, потому что объект `Params` с ними не создаётся.
- `__post_init__` проверяет только сами значения. Проверки, которым нужно состояние системы или контекст (права пользователя, существование объектов, правила агрегатов), остаются в `run` и в домене.
- Адаптер сам решает, как сообщить внешней системе о `ValueError` из `Params` (см. навык конкретного адаптера).
- Результат возвращается в виде датаклассов или простых типов данных. Возвращаемые DTO описываются рядом в том же файле, и между разными usecase НЕ переиспользуются (та же причина, что у `Params`: независимая эволюция контрактов).
- Типизация полная: за границу слоя выходят только типизированные объекты, а не `dict`, `list[dict]` или `Any`.

## Ошибки
- Общие правила оформления ошибок (имена без `Error`, `__str__`, датаклассы не `frozen`) - в разделе "Ошибки" навыка `python-classic-architecture`.
- Ошибки приложения (`AppError`) - для случаев, когда входные данные корректны, но состояние приложения или бизнес-правила не позволяют выполнить usecase: объект не найден, операция недопустима в текущем состоянии. Некорректные входные данные - это не ошибка приложения: их отсекает `__post_init__` параметров через `ValueError` (см. Параметры и результат).
- Все ошибки приложения наследуются от общего базового класса `AppError` из `app/errors.py`. По нему адаптеры отличают ожидаемые ошибки приложения от прочих исключений:
  ```python
  # app/errors.py
  class AppError(Exception):
      """Базовый класс ошибок приложения"""
  ```
- Ошибки запросов объявляются в файле запроса, ошибки команд - в файле команды, общие для нескольких usecase ошибки - в общих модулях app.

## Логирование и транзакции
- Usecase получает `logging.Logger` через конструктор и логирует значимые бизнес-события.
- Usecase не управляет транзакцией и сквозной функциональностью (повторы, замеры и т.п.) сам: они навешиваются на его методы снаружи, сам usecase о них не знает. Иначе каждый usecase дублировал бы обвязку, и её нельзя было бы изменить централизованно в композите; а так код usecase делает только то, что должен, и в тестах не нужны моки повторов, кэшей и прочей обвязки.

## Права
- Если в приложении есть разграничение доступа, usecase сам проверяет права на выполнение действия: права - бизнес-правило. Проверка выполняется в начале `run`, до любых изменений и обращений к хранилищу (fail fast).
- Адаптеры права не проверяют: они только передают в usecase данные о том, кто выполняет действие. Адаптеров несколько (HTTP, бот, очередь) - проверка в каждом дублировалась бы и расходилась, а в usecase она одна и тестируется unit-тестами.

## Commands
- Usecase-команда (Command) предназначена для изменения состояния системы (бизнес-объектов) по заложенным бизнес-правилам.
- Usecase-команды группируются в пакете `commands/use_cases`, внутри - по предметным группам: `use_cases/<group>/<usecase>.py`.
- Для доступа к хранилищу использует абстрактные репозитории доменной модели, имплементации размещаются в адаптерах.
- Типичная команда: извлечь агрегат из репозитория, изменить его через поля или методы, сохранить обратно. Создание - собрать агрегат из параметров и сохранить.
- Бизнес-правила, относящиеся к агрегату, живут в агрегате, а не в команде. Команда оркестрирует: проверяет права, достаёт агрегаты, вызывает их методы, сохраняет, испускает сигналы.
- Рядом с командой в том же файле могут быть описаны дополнительные датаклассы, необходимые для работы UseCase.
- ABC внешней системы, нужной одной команде, объявляется в файле этой команды, нужной нескольким командам - в `commands/<system>.py`. Если система нужна самому домену, ABC объявляется в домене (см. `python-classic-domain`).

## Queries
- Usecase-запрос (Query) предназначен для выдачи данных из системы наружу.
- Usecase-запросы группируются в пакете queries, внутри - по предметным группам: `queries/<group>/<query>.py`.
- Метод run должен быть идемпотентным и не менять состояние системы: тогда запрос можно безопасно повторять и кэшировать, а побочные эффекты чтения ломали бы само разделение команд и запросов.
- Usecase-запрос - конкретный класс. Для доступа к данным он объявляет в том же файле абстрактный гейтвей (ABC), реализация гейтвея размещается в адаптере к хранилищу. Гейтвей не является репозиторием: репозиторий - контракт работы с агрегатами (изменение состояния с инвариантами), а гейтвей - чтение произвольных выборок, и его нельзя использовать как обходной путь для записи.
- Гейтвей возвращает DTO, объявленные в файле запроса.
- Логика запроса (проверка прав, сборка отчёта и т.п.) остаётся в usecase-запросе, а не размазывается по адаптеру.
- queries независимы от commands: запросы НЕ импортируют ничего из `app/commands` (ни доменную модель, ни usecase-команды, ни доменные ошибки). Стороны CQRS эволюционируют отдельно: изменение команды или домена не должно ломать запросы. Если DTO запроса структурно совпадает с доменным объектом или перечислением, он всё равно описывается отдельно в файле запроса (та же логика, что у `Params` выше). Ошибки запроса (например, `GetBookNotFound`) объявляются в файле запроса. Общие для всего app вещи (`app/errors.py`) импортировать можно.
- Сортировка задаётся в параметрах запроса полем с `Literal` или `Enum` допустимых значений - это белый список, который адаптер переводит в имена колонок. Свободная строка сортировки открыла бы SQL-инъекцию и привязала бы контракт app к именам колонок конкретной БД.

## Сигналы
- Для отвязки приложения от адаптеров используется `classic.signals.Hub`. Это синхронная in-process отвязка, а не шина событий: `notify` вызывает реакции последовательно в потоке эмиттера, внутри той же транзакции.
- Контракт сигнала - простой датакласс в `app/commands/signals.py`. Бизнес-параметры, нужные обработчику, передаются в полях сигнала. Контракт доменного события, которое испускает сам домен, объявляется в домене (`domain/events.py`, см. `python-classic-domain`).
- Usecase получает `hub` через конструктор и вызывает `hub.notify(Signal(...))`.
- Подписчик подписывается в своём конструкторе: `hub.add_reaction(Signal, self._on_signal)`. Поэтому подписчик должен быть создан до первого `notify`.
- Подписчики размещаются в адаптерах.
- Сигналы - только те, что нужны по задаче. Не вводить промежуточные сигналы там, где usecase может сам вызвать репозиторий или ABC: подписки на сигнал отслеживаются статически, но это тяжелее, чем переход по прямому вызову в IDE.
