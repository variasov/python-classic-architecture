# Python App Layer in "Classic" Architecture

## Описание

В этом навыке описывается слой приложения (app) - нижний, основной слой.
Общая идея слоёв описана в навыке `python-classic-architecture`.
Слой app может содержать опциональную модель домена, она описана в навыке `python-classic-domain`.

## Когда использовать
- Во время разработки новых команд и запросов.
- Во время ревью бизнес-логики.
- При написании тестов на usecase.

## Структура
Раскладка пакета `app/` - в разделе Layout навыка `python-classic-architecture`.

## Общие правила
- Содержит в себе логику, обеспечивающую потребности бизнеса.
- Не должен содержать обращения к инфраструктуре и другим системам. Вместо прямых обращений приложение должно объявлять абстрактный базовый класс и использовать его. Реализации абстрактного класса выносятся на слой адаптеров, а в usecase попадают через конструктор.
- Запрещено импортировать в app драйверы БД, `classic.db_tools.Engine`, веб-фреймворки, библиотеки парсинга и сериализации и SQL. DTO слоя app - чистые датаклассы стандартной библиотеки.
- Каждое действие в приложении, возможное в системе, должно быть выражено как usecase - класс с публичным методом run.
- Usecase делятся на команды (меняют состояние) и запросы (читают данные). Это CQRS: команды и запросы живут в разных пакетах и не зависят друг от друга.
- Если "usecase" сводится к одному обращению к хранилищу без бизнес-логики, это не usecase, а адаптер. Приложение в этом случае объявляет ABC или испускает сигнал (см. Сигналы).
- К usecase не должно быть обращения из уровня приложения, только из адаптеров. Исключение - доменные usecase, которые вызываются из команд.
- Комментарии и docstring в app не ссылаются на реализации и файлы верхних слоёв. Описание контракта говорит "что это значит", а не "кто это обрабатывает".

## Параметры и результат
- Параметры принимаются usecase в виде датаклассов или простых типов данных, их описание размещается в том же файле, что и usecase. Входные параметры называются `<UseCase>Params`.
- Датаклассы параметров НЕ переиспользуются между usecase и не выносятся в общий файл, даже если структуры совпадают: два usecase с похожими `PatternParams` содержат две независимые копии.
- Как получить `Params` из внешнего представления (HTTP-запроса, сообщения бота, задачи, сообщения очереди), решает адаптер, вызывающий usecase. Он разбирает данные и создаёт датакласс ДО вызова usecase. Поэтому usecase не проверяет структуру и типы данных.
- Все проверки корректности входных параметров выполняются в `__post_init__` датакласса `Params`, а не в `run`: диапазоны, пагинация (`limit` > 0 и не больше максимума, `offset` >= 0), согласованность полей. Так невалидный объект параметров невозможно создать, и `run` работает только с корректными данными.
  ```python
  @dataclass(frozen=True)
  class FindBooksParams:
      MAX_LIMIT: ClassVar[int] = 100
      MIN_SEARCH_LENGTH: ClassVar[int] = 3

      title__contains: str | None = None
      limit: int = 20
      offset: int = 0

      def __post_init__(self) -> None:
          if not 0 < self.limit <= self.MAX_LIMIT:
              raise ValueError(f'limit должен быть от 1 до {self.MAX_LIMIT}')
          if self.offset < 0:
              raise ValueError('offset не может быть отрицательным')
          search = self.title__contains
          if search is not None and len(search) < self.MIN_SEARCH_LENGTH:
              raise ValueError(f'Строка поиска короче {self.MIN_SEARCH_LENGTH} символов')
  ```
- `__post_init__` при нарушении бросает встроенный `ValueError` с понятным сообщением. Отдельные классы ошибок (`AppError`) под каждую проверку параметров не объявляются: некорректные параметры - это ошибка ввода, а не бизнес-ситуация, которую клиенту нужно различать по типу.
- Константы, нужные проверкам (максимумы, минимальные длины), объявляются `ClassVar` на классе параметров.
- `run` не повторяет проверки параметров: некорректные параметры не доходят до usecase, потому что объект `Params` с ними не создаётся.
- `__post_init__` проверяет только сами значения. Проверки, которым нужно состояние системы или контекст (права пользователя, существование объектов, правила агрегатов), остаются в `run` и в домене.
- Адаптер сам решает, как сообщить внешней системе о `ValueError` из `Params` (см. навык конкретного адаптера).
- Результат возвращается в виде датаклассов или простых типов данных. Возвращаемые DTO описываются рядом в том же файле, и между разными usecase НЕ переиспользуются.
- Типизация полная: за границу слоя выходят только типизированные объекты, а не `dict`, `list[dict]` или `Any`.

## Ошибки
- Общие правила оформления ошибок (имена без `Error`, `__str__`, датаклассы не `frozen`) - в разделе "Ошибки" навыка `python-classic-architecture`.
- Ошибки приложения (`AppError`) - для случаев, когда входные данные корректны, но состояние приложения или бизнес-правила не позволяют выполнить usecase: объект не найден, нет права, операция недопустима в текущем состоянии. Некорректные входные данные - это не ошибка приложения: их отсекает `__post_init__` параметров через `ValueError` (см. Параметры и результат).
- Все ошибки приложения наследуются от общего базового класса `AppError` из `app/errors.py`. По нему адаптеры отличают ожидаемые ошибки приложения от прочих исключений:
  ```python
  # app/errors.py
  class AppError(Exception):
      """Базовый класс ошибок приложения"""
  ```
- Ошибки запросов объявляются в файле запроса, ошибки команд - в файле команды, общие для нескольких usecase ошибки - в общих модулях app.

## Текущее время
- Текущее время - внешняя зависимость, как хранилище. Usecase не вызывает `date.today()` и `datetime.now()`, а получает через конструктор `Clock` - ABC, объявленный в `app/clock.py` (общий для команд и запросов):
  ```python
  # app/clock.py
  class Clock(ABC):
      @abstractmethod
      def now(self) -> datetime: ...

      def today(self) -> date:
          return self.now().date()
  ```
- Usecase берёт время один раз в начале `run` и передаёт его во все методы агрегатов и критерии явно (см. `python-classic-domain`):
  ```python
  def run(self, params: ReturnLoanParams) -> None:
      today = self.clock.today()
      loan = self.loans.get_by_id(params.loan_id)
      loan.return_on(today)
      self.loans.save(loan)
  ```
- Если момент времени - часть запроса пользователя (отчёт "на дату", отложенное действие), он передаётся полем `Params`, а не берётся из `Clock`.
- Реализация на системных часах (`SystemClock`) размещается в адаптере. Часовой пояс задаёт реализация: `now()` возвращает aware `datetime`.

## Логирование и транзакции
- Usecase получает `logging.Logger` через конструктор и логирует значимые бизнес-события.
- Usecase не управляет транзакцией и сквозной функциональностью (повторы, замеры и т.п.) сам: они навешиваются на его методы снаружи, сам usecase о них не знает.

## Права
- Если в приложении есть разграничение доступа, usecase сам проверяет права на выполнение действия. Проверка выполняется в начале `run`, до любых изменений и обращений к хранилищу. Отказ - ошибка приложения (`AppError`).
- Адаптеры права не проверяют: они только передают в usecase данные о том, кто выполняет действие.

## Commands
- Usecase-команда (Command) предназначена для изменения состояния системы (бизнес-объектов) по заложенным бизнес-правилам.
- Usecase-команды группируются в пакете `commands/use_cases`, внутри - по предметным группам: `use_cases/<group>/<usecase>.py`.
- Для доступа к хранилищу использует абстрактные репозитории доменной модели, имплементации размещаются в адаптерах.
- Типичная команда: извлечь агрегат из репозитория, изменить его через поля или методы, сохранить обратно. Создание - собрать агрегат из параметров и сохранить.
- Бизнес-правила, относящиеся к агрегату, живут в агрегате, а не в команде. Команда оркестрирует: проверяет права, достаёт агрегаты, вызывает их методы, сохраняет, испускает сигналы.
- Рядом с командой в том же файле могут быть описаны дополнительные датаклассы, необходимые для работы UseCase.
- ABC внешней системы, нужной одной команде, объявляется в файле этой команды, нужной нескольким командам - в `commands/<system>.py`. Если система нужна самому домену, ABC объявляется в домене (см. `python-classic-domain`).

## Queries
- Usecase-запрос (Query) предназначен для выдачи данных из системы наружу.
- Usecase-запросы группируются в пакете queries, внутри - по предметным группам: `queries/<group>/<query>.py`.
- Метод run должен быть идемпотентным и не менять состояние системы.
- Usecase-запрос - конкретный класс. Для доступа к данным он объявляет в том же файле абстрактный гейтвей (ABC), реализация гейтвея размещается в адаптере к хранилищу. Гейтвей не является репозиторием: через него нельзя изменять состояние.
- Гейтвей возвращает DTO, объявленные в файле запроса.
- Логика запроса (проверка прав, сборка отчёта и т.п.) остаётся в usecase-запросе, а не размазывается по адаптеру.
- queries независимы от commands: запросы НЕ импортируют ничего из `app/commands` (ни доменную модель, ни usecase-команды, ни доменные ошибки). Если DTO запроса структурно совпадает с доменным объектом или перечислением, он всё равно описывается отдельно в файле запроса. Ошибки запроса (например, `GetBookNotFound`) объявляются в файле запроса. Общие для всего app вещи (`app/errors.py`, `app/clock.py`) импортировать можно.
- Сортировка задаётся в параметрах запроса полем с `Literal` или `Enum` допустимых значений - это белый список, который адаптер переводит в имена колонок.

## Сигналы
- Для отвязки приложения от адаптеров используется `classic.signals.Hub`. Это синхронная in-process отвязка, а не шина событий: `notify` вызывает реакции последовательно в потоке эмиттера, внутри той же транзакции.
- Контракт сигнала - простой датакласс в `app/commands/signals.py`. Бизнес-параметры, нужные обработчику, передаются в полях сигнала.
- Usecase получает `hub` через конструктор и вызывает `hub.notify(Signal(...))`.
- Подписчик подписывается в своём конструкторе: `hub.add_reaction(Signal, self._on_signal)`. Поэтому подписчик должен быть создан до первого `notify`.
- Подписчики размещаются в адаптерах.
- Сигналы - только те, что нужны по задаче. Не вводить промежуточные сигналы там, где usecase может сам вызвать репозиторий или ABC.
