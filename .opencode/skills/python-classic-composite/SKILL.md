# Python Composite Layer in "Classic" Architecture

## Описание

В этом навыке описывается композит - верхний слой приложения.
Общая идея слоёв описана в навыке `python-classic-architecture`.

## Когда использовать
- При добавлении нового usecase, репозитория, гейтвея, адаптера или точки входа - всё это нужно собрать в композите.
- При настройке транзакций, аспектов, подписчиков на сигналы.
- При написании интеграционных тестов собранного приложения.

## Назначение
- Здесь находится инстанцирование нужных классов, передача инстансов друг другу для удовлетворения зависимостей.
- Композит - единственное место, где известны конкретные реализации ABC. Остальные слои получают зависимости через конструктор.
- Здесь размещаются инстансы настроек адаптеров (классы настроек описаны в самих адаптерах). Инстанцирование настроек - момент, когда программа явно требует окружение: у чувствительных настроек нет дефолтов, поэтому без обязательных переменных окружения сборка падает сразу, а не при первом обращении. Правила настроек - в `python-classic-architecture`.
- Бизнес-логики в композите нет.
- Композит не содержит stubs и переключателей "тестового режима": в тестах он собирается так же, как в бою, отличаются только настройки.

## Структура
- Каждый инстанс должен находиться в своем файле (правило «класс = файл», перенесённое на инстансы: инстанс находится по имени класса). В целом этот слой зеркалит структуру других слоев - расположение предсказуемо, не нужно думать о размещении и переиспользовании инстансов, и достигается максимальное переиспользование кода между разными точками входа:
  ```
  composites/
    aspects/<aspect>.py         # сквозная функциональность вне адаптеров (retry и т.п.)
    app/hub.py                  # инстанс Hub
    app/commands/<usecase>.py   # инстанс usecase-команды + обёртки
    app/queries/<query>.py      # инстанс usecase-запроса + обёртки
    infra/db/engine.py          # Engine
    infra/db/settings.py        # инстанс настроек БД
    infra/db/repos/<repo>.py
    infra/db/gateways/<gateway>.py
    infra/db/subscribers/<subscriber>.py
    integrations/<system>/      # инстансы настроек и клиентов
    interfaces/<entry>/         # точка входа
  ```

## Точки входа
- Здесь размещаются точки входа в приложение, по пакету на процесс (`interfaces/api`, `interfaces/<name>_worker`, `interfaces/<name>_scheduler`).
- Запускать точку входа предпочтительно как модуль, например `python -m library.composites.interfaces.api`, поэтому точка входа содержит `__main__.py`.
- Импорт модулей композита только создаёт инстансы и не имеет других побочных эффектов: соединения с БД и внешними системами при импорте не открываются, а запуск сервера, планировщика или воркера, чтение аргументов командной строки размещаются только в `__main__.py`. Это позволяет импортировать композит в тестах.
- Устройство точки входа конкретного адаптера описано в его навыке (например, `python-classic-adapters-http-api`).
- Планировщик - `classic.scheduler.Scheduler`: задача добавляется `scheduler.by_cron(schedule='0 9 * * *', job=fn, task_name='NAME')`, запуск - `scheduler.run()`. `Hub` не вызываемый, поэтому `job=lambda: hub.notify(Signal(...))`.

## Транзакции и аспекты
- Транзакции и аспекты навешиваются только здесь, обёрткой метода инстанса. Сами классы о них не знают: декораторы транзакций и аспектов в коде app и адаптеров не пишутся - декоратор привязал бы класс к конкретной обвязке, в тестах её пришлось бы обходить, а выбор границ транзакции и аспектов перестал бы быть решением сборки.
- Обернуть можно любой публичный метод любого класса из любого слоя: usecase, репозитория, гейтвея, клиента интеграции, подписчика, ресурса. Что и чем оборачивать, решается при сборке.

### Транзакции
- Транзакция предоставляется адаптером к хранилищу (например, `engine.transaction` из `composites/infra/db/engine.py`), поэтому она не аспект и в `aspects/` не размещается: она привязана к конкретному Engine и его соединению, это не универсальная сквозная функциональность; при этом навешиваться может на методы разных слоёв.
  ```python
  register_reader = RegisterReader(readers=readers_repo, logger=logger)
  register_reader.run = engine.transaction(register_reader.run)
  ```
- Типичная граница транзакции - метод `run` команды. Запрос по умолчанию работает в автокоммите (транзакция не навешивается); транзакция для запроса - только при необходимости: когда несколько обращений гейтвея внутри одного запроса должны видеть согласованный снимок данных, без транзакции данные могли бы измениться между чтениями. Методы, которые всегда вызываются изнутри уже открытой транзакции (доменные usecase, методы репозиториев и гейтвеев при вызове из usecase), транзакцией повторно не оборачиваются. Отдельная транзакция нужна методу, который сам является входом в работу с БД, например подписчику, который вызывается вне usecase, или задаче планировщика.

### Аспекты
- Аспект - сквозная функциональность, не относящаяся к конкретному адаптеру, например, повторы через tenacity. Аспекты размещаются в `composites/aspects/<aspect>.py`.
- В `aspects/` не размещается то, что принадлежит конкретному слою или адаптеру: транзакции (адаптер к БД), `Hub` (app), настройки и клиенты адаптеров.
  ```python
  # composites/aspects/retry.py
  from tenacity import retry, stop_after_attempt, wait_exponential

  retry_on_failure = retry(
      stop=stop_after_attempt(3),
      wait=wait_exponential(max=10),
      reraise=True,
  )
  ```
  ```python
  # composites/integrations/catalog/client.py
  catalog_client = CatalogClient(settings=catalog_settings)
  catalog_client.get_book = retry_on_failure(catalog_client.get_book)
  ```

## Сигналы
- `Hub` относится к слою app (через него usecase испускают сигналы), поэтому общий инстанс `hub = Hub()` размещается в `composites/app/hub.py`.
- Подписчики на сигналы инстанцируются в композите; импорт модуля с инстансом подписывает его на сигнал.
- Каждая точка входа импортирует модули всех подписчиков на сигналы, которые могут быть испущены в её процессе: подписка происходит при импорте (в конструкторе подписчика), неимпортированный подписчик не создан, и его сигнал молча потеряется. На это обращается внимание при тестировании: тесты композита проверяют, что подписчики зарегистрированы.

## Запекание инстансов
- Инстанс в композите создаётся прямо в модуле при импорте, и это единственный инстанс на процесс: модуль кэшируется в `sys.modules`, повторной сборки не бывает, а другим точкам входа инстанс доступен через импорт того же файла. Сборка одноразова, поэтому функция-фабрика для одиночного инстанса не заводится.
  ```python
  # composites/app/commands/return_loan.py
  return_loan = ReturnLoan(loans=loans_repo, logger=logger)
  return_loan.run = engine.transaction(return_loan.run)
  ```
- Обёртки (транзакции, аспекты) навешиваются на этот же модульный инстанс сразу после создания - выбор обвязки остаётся решением сборки.

## Тестирование
Тесты композита - e2e-тесты собранного приложения: настоящий композит, тестовая БД, stub-серверы внешних систем. Проверяется сборка, а не бизнес-логика (см. пирамиду в `python-classic-architecture`).
Подробные правила (фикстура `test_env`, импорт композита внутри session-фикстуры, что проверять) - в `references/testing.md` этого навыка. Читай его, когда пишешь или правишь тесты композита.
