# Python Composite Layer in "Classic" Architecture

## Описание

В этом навыке описывается композит - верхний слой приложения.
Общая идея слоёв описана в навыке `python-classic-architecture`.

## Когда использовать
- При добавлении нового usecase, репозитория, гейтвея, адаптера или точки входа - всё это нужно собрать в композите.
- При настройке транзакций, аспектов, подписчиков на сигналы.
- При написании интеграционных тестов собранного приложения.

## Назначение
- Здесь находится инстанцирование нужных классов, передача инстансов друг другу для удовлетворения зависимостей.
- Композит - единственное место, где известны конкретные реализации ABC. Остальные слои получают зависимости через конструктор.
- Здесь размещаются инстансы настроек адаптеров (классы настроек описаны в самих адаптерах).
- Бизнес-логики в композите нет.
- Композит не содержит stubs и переключателей "тестового режима": в тестах он собирается так же, как в бою, отличаются только настройки.

## Структура
- Каждый инстанс должен находиться в своем файле. В целом этот слой зеркалит структуру других слоев:
  ```
  composites/
    aspects/<aspect>.py         # сквозная функциональность вне адаптеров (retry и т.п.)
    app/hub.py                  # инстанс Hub
    app/commands/<usecase>.py   # инстанс usecase-команды + обёртки
    app/queries/<query>.py      # инстанс usecase-запроса + обёртки
    infra/db/engine.py          # Engine
    infra/db/settings.py        # инстанс настроек БД
    infra/db/repos/<repo>.py
    infra/db/gateways/<gateway>.py
    infra/db/subscribers/<subscriber>.py
    infra/clock/system.py       # инстанс SystemClock
    integrations/<system>/      # инстансы настроек и клиентов
    interfaces/<entry>/         # точка входа
  ```

## Точки входа
- Здесь размещаются точки входа в приложение, по пакету на процесс (`interfaces/api`, `interfaces/<name>_worker`, `interfaces/<name>_scheduler`).
- Запускать точку входа предпочтительно как модуль, например `python -m library.composites.interfaces.api`, поэтому точка входа содержит `__main__.py`.
- Импорт модулей композита только создаёт инстансы и не имеет других побочных эффектов: соединения с БД и внешними системами при импорте не открываются, а запуск сервера, планировщика или воркера, чтение аргументов командной строки размещаются только в `__main__.py`. Это позволяет импортировать композит в тестах.
- Устройство точки входа конкретного адаптера описано в его навыке (например, `python-classic-adapters-http-api`).
- Планировщик - `classic.scheduler.Scheduler`: задача добавляется `scheduler.by_cron(schedule='0 9 * * *', job=fn, task_name='NAME')`, запуск - `scheduler.run()`. `Hub` не вызываемый, поэтому `job=lambda: hub.notify(Signal(...))`.

## Транзакции и аспекты
- Транзакции и аспекты навешиваются только здесь, обёрткой метода инстанса. Сами классы о них не знают: декораторы транзакций и аспектов в коде app и адаптеров не пишутся.
- Обернуть можно любой публичный метод любого класса из любого слоя: usecase, репозитория, гейтвея, клиента интеграции, подписчика, ресурса. Что и чем оборачивать, решается при сборке.

### Транзакции
- Транзакция предоставляется адаптером к хранилищу (например, `engine.transaction` из `composites/infra/db/engine.py`), поэтому она не аспект и в `aspects/` не размещается.
  ```python
  register_reader = RegisterReader(readers=readers_repo, logger=logger)
  register_reader.run = engine.transaction(register_reader.run)
  ```
- Типичная граница транзакции - метод `run` usecase, и команды, и запроса (запрос читает в одной транзакции). Методы, которые всегда вызываются изнутри уже открытой транзакции (доменные usecase, методы репозиториев и гейтвеев при вызове из usecase), транзакцией повторно не оборачиваются. Отдельная транзакция нужна методу, который сам является входом в работу с БД, например подписчику, который вызывается вне usecase, или задаче планировщика.

### Аспекты
- Аспект - сквозная функциональность, не относящаяся к конкретному адаптеру, например, повторы через tenacity. Аспекты размещаются в `composites/aspects/<aspect>.py`.
- В `aspects/` не размещается то, что принадлежит конкретному слою или адаптеру: транзакции (адаптер к БД), `Hub` (app), настройки и клиенты адаптеров.
  ```python
  # composites/aspects/retry.py
  from tenacity import retry, stop_after_attempt, wait_exponential

  retry_on_failure = retry(
      stop=stop_after_attempt(3),
      wait=wait_exponential(max=10),
      reraise=True,
  )
  ```
  ```python
  # composites/integrations/catalog/client.py
  catalog_client = CatalogClient(settings=catalog_settings)
  catalog_client.get_book = retry_on_failure(catalog_client.get_book)
  ```

## Сигналы
- `Hub` относится к слою app (через него usecase испускают сигналы), поэтому общий инстанс `hub = Hub()` размещается в `composites/app/hub.py`.
- Подписчики на сигналы инстанцируются в композите; импорт модуля с инстансом подписывает его на сигнал.
- Каждая точка входа импортирует модули всех подписчиков на сигналы, которые могут быть испущены в её процессе.

## Фабрики
- Чтобы тесты могли повторить сборку без импорта глобальных инстансов, сборка нетривиальных объектов оформляется в композите функцией-фабрикой, а модульный инстанс создаётся её вызовом:
  ```python
  # composites/app/commands/return_loan.py
  def create_return_loan(
      loans: LoansRepo,
      clock: Clock,
      engine: Engine,
      logger: logging.Logger,
  ) -> ReturnLoan:
      return_loan = ReturnLoan(loans=loans, clock=clock, logger=logger)
      return_loan.run = engine.transaction(return_loan.run)
      return return_loan


  return_loan = create_return_loan(
      loans=loans_repo, clock=clock, engine=engine, logger=logger
  )
  ```
- Сборка точки входа конкретного адаптера тоже оформляется фабрикой, её устройство описано в навыке адаптера.
- Unit-тесты и тесты адаптеров импортируют фабрики, но не инстансы. Инстансы импортируют только тесты композита.

## Тестирование
Тесты композита - верхний, интеграционный (e2e) уровень пирамиды (см. `python-classic-architecture`). Они проверяют, что приложение собрано правильно, а не бизнес-логику.

### Подход
- Тест импортирует настоящий композит и работает с ним как внешний клиент через точку входа. Как обращаться к точке входа конкретного адаптера, описано в его навыке.
- Своя инфраструктура - настоящая тестовая БД (фикстуры `migrated_db`, `raw_db` из `python-classic-adapters-sql-db`).
- Внешние системы подменяются на сетевом уровне: тест поднимает stub-сервер (`pytest-httpserver` для HTTP, тестовые аналоги для других протоколов), а адрес системы передаётся в композит настройками.
- Тесты лежат в `tests/composites/test_<entry>.py`, по файлу на точку входа, фикстуры - в `tests/composites/conftest.py`.

### Сборка тестового окружения
- Настройки читаются при импорте композита, а модуль кэшируется в `sys.modules`. Поэтому:
  - переменные окружения выставляются до первого импорта композита;
  - композит импортируется только внутри session-фикстуры, никогда в начале тестового модуля;
  - на весь прогон действует одна конфигурация. Сценарии различаются ответами stub-сервера и данными, а не настройками.
- Тесты композита используют те же переменные окружения, что и бой, поэтому фикстура обязана убедиться, что они указывают на тестовую БД.
  ```python
  # tests/composites/conftest.py
  @pytest.fixture(scope='session')
  def catalog_server() -> Iterator[HTTPServer]:
      server = HTTPServer()
      server.start()
      yield server
      server.stop()


  @pytest.fixture(scope='session')
  def test_env(test_db_settings, migrated_db, catalog_server) -> Iterator[None]:
      with pytest.MonkeyPatch.context() as env:
          env.setenv('DB_HOST', test_db_settings.TEST_DB_HOST)
          env.setenv('DB_NAME', test_db_settings.TEST_DB_NAME)
          ...
          env.setenv('CATALOG_URL', catalog_server.url_for('/'))
          yield


  @pytest.fixture(scope='session')
  def scheduler_jobs(test_env):
      from library.composites.interfaces.reminders_scheduler import jobs

      return jobs
  ```
  Фикстура `test_env` выставляет окружение, фикстуры точек входа зависят от неё и импортируют композит внутри себя.
- Глобальное состояние композита (engine, hub с подписчиками) общее на все тесты. Изоляция данных - как в тестах адаптера к БД: данные создаются через API приложения и удаляются в teardown только созданные тестом записи.
- Точки входа без HTTP (планировщик, воркер): из модуля композита импортируется инстанс задачи или обработчика и вызывается напрямую. `scheduler.run()` и бесконечные циклы в тестах не запускаются.

### Что проверять
- Каждый вход (маршрут, задача, обработчик) подключён и доходит до БД: один успешный сценарий на usecase, результат читается обратно через точку входа.
- Транзакции навешены: при ошибке в середине команды изменения откатываются (проверка через `raw_db`).
- Подписчики на сигналы зарегистрированы в этой точке входа: после команды видны результаты реакции.
- Аспекты навешены: например, при временной ошибке stub-сервера retry приводит к успеху.
- Интеграции подключены: запрос к внешней системе дошёл до stub-сервера, ответ stub-сервера отразился в результате.
- Обработка ошибок, настроенная в точке входа, работает в собранном приложении.
- Не перебираются повторно бизнес-правила, фильтры гейтвеев и варианты разбора запросов - они покрыты нижними уровнями.
- `__main__.py` не тестируется: он тривиален и только запускает уже проверенную сборку.
