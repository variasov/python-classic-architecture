# Тестирование: python-classic-composite
Тесты композита - верхний, интеграционный (e2e) уровень пирамиды (см. `python-classic-architecture`). Они проверяют, что приложение собрано правильно, а не бизнес-логику.

### Подход
- Тест импортирует настоящий композит и работает с ним как внешний клиент через точку входа. Как обращаться к точке входа конкретного адаптера, описано в его навыке.
- Своя инфраструктура - настоящая тестовая БД (фикстуры `migrated_db`, `raw_db` из `python-classic-adapters-sql-db`).
- Внешние системы подменяются на сетевом уровне: тест поднимает stub-сервер (`pytest-httpserver` для HTTP, тестовые аналоги для других протоколов), а адрес системы передаётся в композит настройками.
- Тесты лежат в `tests/composites/test_<entry>.py`, по файлу на точку входа, фикстуры - в `tests/composites/conftest.py`.

### Сборка тестового окружения
- Настройки читаются при импорте композита, а модуль кэшируется в `sys.modules`. Поэтому:
  - тестовое окружение (`.env.test`) загружается в переменные окружения корневым
    `tests/conftest.py` до первого импорта композита (см. «Тестовое окружение настроек»
    в `references/testing.md` навыка `python-classic-architecture`);
  - композит импортируется только внутри session-фикстуры, никогда в начале тестового модуля;
  - на весь прогон действует одна конфигурация. Сценарии различаются ответами stub-сервера и данными, а не настройками.
- Значения БД и остальных настроек уже пришли из тестового окружения. Фикстура `test_env`
  выставляет только переменные, значения которых известны в момент запуска тестов - адреса
  stub-серверов: без них композит не соберётся, у боевых настроек нет дефолтов.
  ```python
  # tests/composites/conftest.py
  @pytest.fixture(scope='session')
  def catalog_server() -> Iterator[HTTPServer]:
      server = HTTPServer()
      server.start()
      yield server
      server.stop()


  @pytest.fixture(scope='session')
  def test_env(migrated_db, catalog_server) -> Iterator[None]:
      with pytest.MonkeyPatch.context() as env:
          env.setenv('CATALOG_URL', catalog_server.url_for('/'))
          yield


  @pytest.fixture(scope='session')
  def scheduler_jobs(test_env):
      from library.composites.interfaces.reminders_scheduler import jobs

      return jobs
  ```
  Фикстура `test_env` выставляет окружение, фикстуры точек входа зависят от неё и импортируют композит внутри себя.
- Глобальное состояние композита (engine, hub с подписчиками) общее на все тесты. Изоляция данных - как в тестах адаптера к БД: данные создаются через API приложения и удаляются в teardown только созданные тестом записи.
- Точки входа без HTTP (планировщик, воркер): из модуля композита импортируется инстанс задачи или обработчика и вызывается напрямую. `scheduler.run()` и бесконечные циклы в тестах не запускаются.

### Что проверять
- Каждый вход (маршрут, задача, обработчик) подключён и доходит до БД: один успешный сценарий на usecase, результат читается обратно через точку входа.
- Транзакции навешены: при ошибке в середине команды изменения откатываются (проверка через `raw_db`).
- Подписчики на сигналы зарегистрированы в этой точке входа: после команды видны результаты реакции.
- Аспекты навешены: например, при временной ошибке stub-сервера retry приводит к успеху.
- Интеграции подключены: запрос к внешней системе дошёл до stub-сервера, ответ stub-сервера отразился в результате.
- Обработка ошибок, настроенная в точке входа, работает в собранном приложении.
- Не перебираются повторно бизнес-правила, фильтры гейтвеев и варианты разбора запросов - они покрыты нижними уровнями.
- `__main__.py` не тестируется: он тривиален и только запускает уже проверенную сборку.
