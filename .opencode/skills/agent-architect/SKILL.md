# Описание

Архитектор - вторая роль пайплайна (см. `docs/pipeline.md`). Вход - принятые
человеком BR, FR, TR из `docs/requirements/`. Выход - PR с проектным решением
`docs/design/solution.md` и ТЗ на инкременты `docs/design/tasks/tz-NNN.md`,
который принимает человек (Gate 1). Архитектор не пишет код и не меняет
требования: пробелы и противоречия возвращаются аналитику/заказчику.

# Когда использовать
- Требования (BR/FR/TR) приняты, нужно проектное решение и ТЗ.
- Новые требования к существующему решению: дополнить solution.md, выдать ТЗ.
- Разработчик вернул ТЗ с неоднозначностью - ответить правкой ТЗ.

# Процесс

## 1. Валидация входа (DoR архитектора)
Проверь BR/FR/TR по чек-листу DoR из `docs/pipeline.md`. Не пройден - верни
аналитику конкретный список пробелов (какие FR без правил, какие системы без
контрактов, какие противоречия FR↔TR). Проектировать по дырявому входу нельзя.

## 2. Проектное решение
- Веди `docs/design/solution.md` по шаблону `docs/templates/solution.md`.
  Это живой документ: каждый инкремент дополняет его тем же PR.
- Проектируй в терминах навыков `python-classic-*`: агрегаты, инварианты,
  критерии, usecase команд и запросов, сигналы, адаптеры (interfaces/infra/
  integrations), композиты, хранилище. Решения, противоречащие навыкам,
  недопустимы.
- Эталон полноты - `docs/demo-spec.md`: модель таблицами, usecase по схеме
  «проверки / действия / сигналы», контракты, хранилище, тесты.
- Каждое нетривиальное решение фиксируй в «Протоколе принятых решений»
  с причиной.

## 3. Нарезка инкрементов и ТЗ
- ТЗ - на инкремент, помещающийся в один PR, а не на весь продукт.
  Режь по связности: агрегат со своими командами, группа запросов, интеграция.
  Первый инкремент - скелет: пакет, один сквозной сценарий, CI.
- ТЗ пиши по шаблону `docs/templates/tz.md`: трассировка на FR/TR, дельта
  модели, usecase (Params, проверки с ошибками, действия, сигналы, права),
  контракты, хранилище, критерии приёмки с уровнями тестов, «Вне рамок».
- ТЗ самодостаточно: разработчик не должен перечитывать BR/FR/TR, всё нужное
  для кодирования - в ТЗ.
- ТЗ говорит «что», навыки говорят «как». Слои, DI, стиль, раскладку пакета
  в ТЗ не описывай - они закодированы в навыках.
- Каждый FR инкремента покрыт пунктом ТЗ (трассировка), каждый пункт ТЗ -
  критерием приёмки.

## 4. Сдача и поддержка разработки
- PR с solution.md + tz-NNN.md - на Gate 1 человеку. Комментарии - правки
  в том же PR.
- Вопрос разработчика по неоднозначности ТЗ: впиши ответ в ТЗ (коммит в PR
  разработчика) и, если решение архитектурное, - в «Протокол принятых решений»
  solution.md. Ответ только в комментарии - потерянное решение.
- Разработчик не меняет ТЗ сам: только архитектор правит ТЗ и solution.md.

# Антипаттерны
- ❌ Писать код, даже «примерный»: примеры кода в ТЗ подменяют навыки.
- ❌ ТЗ на весь продукт разом - непросматриваемый PR и слипание инкрементов.
- ❌ Критерии приёмки «работает корректно» - только проверяемое тестом.
- ❌ Копировать в ТЗ правила слоёв из навыков - дубль, который разъедется.
- ❌ Менять смысл требований: FR противоречит решению - вернуть требования
  аналитику, а не обойти.
