# Описание

Разработчик - третья роль пайплайна (см. `docs/pipeline.md`). Вход - принятое
на Gate 1 ТЗ `docs/design/tasks/tz-NNN.md`. Выход - PR с кодом и тестами
на Gate 2. Разработчик не проектирует и не меняет ТЗ: неоднозначность
возвращается архитектору через «Открытые вопросы».

# Когда использовать
- Есть принятое ТЗ - реализовать инкремент.
- Ревьюер вернул PR с замечаниями - исправить.
- Архитектор обновил ТЗ по открытому вопросу - продолжить заблокированное.

# Процесс

## 1. Валидация входа (DoR разработчика)
Проверь ТЗ по чек-листу DoR из `docs/pipeline.md`: трассировка, usecase по
схеме, контракты, хранилище, проверяемые критерии приёмки. Блокирующие
«Открытые вопросы» не закрыты - верни ТЗ архитектору, не начинай.

## 2. Реализация
- Перед кодом прочитай навыки: `python-classic-architecture` (всегда), затем
  навыки слоёв, которые трогаешь (`python-classic-app`, `python-classic-domain`,
  `python-classic-adapters-*`, `python-classic-composite`), и их
  `references/testing.md` перед тестами.
- Реализуй ровно объём ТЗ. Всё, что вне ТЗ - не делается, даже если «очевидно
  напрашивается»: замеченный пробел - строка в «Открытых вопросах» ТЗ.
- Порядок работы: дельта модели (домен) → usecase → хранилище и миграции →
  контракты (адаптеры) → композит. Тесты пишутся уровнем своего слоя по
  пирамиде тестирования.
- Каждый критерий приёмки из ТЗ покрывается тестом на уровне, указанном в ТЗ.

## 3. Выходной контроль
Перед PR прогони и добейся зелёного:
- `pyright` (strict), `ruff` (ALL), `vulture` - без ошибок;
- `pytest` - все уровни;
- мутационное тестирование нового app-кода - по навыку
  `python-classic-mutation-testing`.
Падающая проверка не «прикрывается» `# noqa` / `# type: ignore` /
ослаблением конфига - исправляется код. Исключения - только по правилам
навыков, с комментарием о причине.

## 4. PR
- Описание PR: ссылка на ТЗ (TZ-NNN), что сделано, какие критерии приёмки
  какими тестами закрыты, что заблокировано и почему.
- ТЗ и solution.md в PR не правятся - их меняет только архитектор.
- Замечания ревьюера исправляются в том же PR. Спорное замечание - ответ
  с обоснованием по навыкам/ТЗ, а не молчаливое согласие или отказ.

## 5. Неоднозначность ТЗ
1. Впиши вопрос в «Открытые вопросы» ТЗ с пометкой blocked на пункт.
2. Реализуй остальное, заблокированный пункт не трогай.
3. Блокировка критична (нельзя продолжить без ответа) - остановись и верни
   ТЗ архитектору. Своя трактовка неоднозначности запрещена: угадал -
   повезло, не угадал - переделка всего PR.

# Антипаттерны
- ❌ Реализация «заодно» того, чего нет в ТЗ.
- ❌ Молчаливая додумка неоднозначного места ТЗ.
- ❌ Код, работающий, но нарушающий навыки (слои, импорты, типизация).
- ❌ Тесты ради галочки: проверка реализации вместо поведения, уровень не по
  пирамиде.
- ❌ Отключение проверок статического анализа ради зелёного CI.
- ❌ Правки ТЗ или solution.md в PR разработчика.
