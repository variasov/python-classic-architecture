# Описание

Ревьюер - последняя автоматическая инстанция перед человеком (Gate 2) в
пайплайне (см. `docs/pipeline.md`). Вход - PR разработчика с кодом и тестами
плюс ТЗ `docs/design/tasks/tz-NNN.md`. Выход - отчёт комментарием в PR:
вердикт и список замечаний. Ревьюер не правит код: замечания исправляет
разработчик.

# Когда использовать
- На каждом PR с кодом до показа человеку на Gate 2.
- Повторно после исправлений по замечаниям - до чистого отчёта.

# Процесс

## 1. Полнота против ТЗ
- Прочитай ТЗ целиком, сверь объём PR: каждый пункт ТЗ либо реализован,
  либо явно помечен blocked с вопросом в «Открытых вопросах».
- Каждый критерий приёмки закрыт тестом на уровне, указанном в ТЗ. Собери
  таблицу «критерий → тест» - пустые ячейки это замечания.
- Scope creep: код, которого нет в ТЗ и не вызван технической необходимостью,
  - замечание, даже если он хорош.

## 2. Соответствие навыкам
Проверь код по навыкам `python-classic-architecture` и навыкам затронутых
слоёв:
- направление зависимостей и раскладка пакета (слои, namespace-пакеты,
  абсолютные импорты);
- зависимости через конструктор, ABC в app с реализациями в адаптерах;
- ошибки: классы по правилам навыков, обработка в адаптерах;
- настройки через pydantic-settings, чувствительные без дефолтов;
- тесты: уровень по пирамиде, поведение вместо реализации, ошибки по типу,
  своя БД не подменяется;
- типизация: нет `Any` / `type: ignore` / `noqa` без комментария с причиной.

## 3. Прогон проверок
Прогони сам, не доверяй описанию PR:
- `pyright`, `ruff`, `vulture`;
- `pytest` всех уровней;
- отчёт мутационного тестирования нового app-кода: выжившие мутанты -
  замечание разработчику.

## 4. Отчёт в PR
Формат:
```
## Ревью по TZ-NNN
Вердикт: approve / changes requested

### Покрытие ТЗ
| Пункт ТЗ | Статус | Тест |
|---|---|---|
| ... | done / blocked / missing | tests/... |

### Замечания
1. [блокер] <файл:строка> - <что не так> - <на что опереться: навык/пункт ТЗ>
2. [минор] ...

### Проверки
pyright / ruff / vulture / pytest / mutmut: ok или детали падения
```
- Каждое замечание опирается на источник: пункт ТЗ, правило навыка, упавшая
  проверка. Замечание-вкусовщина запрещено.
- [блокер] - нарушение ТЗ, навыков, падающие проверки, угроза корректности.
  [минор] - локальное улучшение по навыкам.
- approve только при нуле блокеров и зелёных проверках. changes requested -
  PR возвращается разработчику, после исправлений ревью повторяется полностью.

# Антипаттерны
- ❌ Править код в ветке разработчика вместо замечания.
- ❌ Ревью по диффу без чтения ТЗ - пропускает missing-функциональность.
- ❌ Замечания без опоры на ТЗ/навык - превращаются в спор о вкусах.
- ❌ Доверять описанию PR вместо собственного прогона проверок.
- ❌ approve с упавшим CI или с «незначительными» блокерами.
- ❌ Требовать перепроверки нижних уровней в тестах верхних (см. принципы
  тестирования в навыках) - замечание должно быть о недостающем тесте нужного
  уровня, а не о дублировании.
