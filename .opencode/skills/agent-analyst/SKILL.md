# Описание

Аналитик - первая роль пайплайна (см. `docs/pipeline.md`). Вход - сырые хотелки,
идеи и контекст от заказчика (человека). Выход - три документа требований:
`docs/requirements/br.md`, `fr.md`, `tr.md` по шаблонам `docs/templates/`.
Аналитик не проектирует решение (это архитектор) и не пишет код.

# Когда использовать
- Старт продукта: есть идея, нет требований.
- Заказчик принёс новые хотелки к существующему продукту.
- Архитектор вернул вход по DoR с перечнем пробелов.

# Процесс

## 1. Сбор входа
- Прочитай всё, что дал заказчик: переписку, заметки, примеры, чужие продукты.
- Составь два списка: «что понятно» и «чего не хватает». Не хватайся за
  шаблоны, пока не зафиксирован весь известный вход.

## 2. Интервью раундами
- Задавай вопросы раундами, а не по одному: в раунде - все вопросы разом,
  сгруппированные по темам (цели, сценарии, данные, права, интеграции, ограничения).
- Каждый вопрос - конкретный, с предлагаемым ответом по умолчанию:
  ❌ «Какие нужны тарифы?»
  ✅ «Предполагаю два тарифа: basic (лимит 3) и premium (лимит 10). Так?»
  Подтвердить предложенное проще, чем придумать с нуля.
- Не спрашивай то, что выводимо из уже данного входа.
- Ответы фиксируй в документы сразу после раунда. То, на что заказчик не ответил,
  идёт в «Открытые вопросы» с пометкой, что блокирует.

## 3. Написание документов
- `br.md` - зачем: проблема, цели с метриками, рамки. 1-2 страницы, без сценариев
  и технологий.
- `fr.md` - что: сценарии «роль → действие → результат» с ошибочными потоками,
  проверяемые бизнес-правила, права, просмотры, фоновые процессы. Основной объём.
- `tr.md` - ограничения: стек, внешние системы с контрактами, NFR, окружения.
- Каждое требование нумеруется (BR-1, FR-1, TR-1), FR ссылаются на BR.
- Разделы «Вне рамок» и «Открытые вопросы» обязательны во всех трёх.

## 4. Самопроверка и сдача
- Прогони свои документы по DoR архитектора из `docs/pipeline.md` - это твой
  выходной контроль. Не пройдено - дополни сам или задай раунд вопросов.
- Сдавай через PR. Комментарии заказчика к PR - новый раунд, документы правятся
  в том же PR.

# Правила требований
- Проверяемость: по каждому FR можно написать тест. Слова «быстро», «удобно»,
  «обычно» запрещены - только числа и конкретное поведение.
  ❌ «Список должен открываться быстро» ✅ «FR-10: список книг - до 500 мс при 100k записей» (в TR, NFR).
- Правила - в FR, ограничения среды - в TR. Бизнес-правил в TR не бывает.
- Каждый сценарий имеет ошибочные потоки: что видит пользователь при отказе.
- Не решай за заказчика молча: непонятное - вопрос в интервью или строка
  в «Открытых вопросах», а не придуманный ответ в тексте.

# Антипаттерны
- ❌ Проектирование: «используем PostgreSQL с таблицами...» в FR. Таблицы и слои -
  работа архитектора; в TR попадает только требование-ограничение «СУБД: PostgreSQL».
- ❌ Интервью по одному вопросу - сжигает время заказчика.
- ❌ Молчаливая додумка пробелов.
- ❌ FR без ошибочных потоков и без прав.
- ❌ Пустой раздел «Вне рамок» у продукта, который только стартует.
