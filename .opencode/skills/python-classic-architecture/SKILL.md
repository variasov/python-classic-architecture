# Описание

В этом навыке описывается реализация "Классической" архитектуры в проекте на Python. 
"Классическая" архитектура - смесь известных концепций, известных в сообществе:
- Чистая архитектура
- Domain Driven Design
- CQRS


# Когда использовать
- Когда пользователь запрашивает ревью код или архитектуры.
- Во время разработки новых фич в Python-приложении.

# Layout
- В корне проекта должен быть pyproject.toml.
- Приложение должно быть представлено namespaced Python-пакетом. Пакет должен лежать в src.
- Весь пакет состоит из namespace, ни одного файла __init__.py быть не должно.
- Все импорты должны быть абсолютными и размещаться в начале файла.
- Все классы принимают зависимости через конструктор.
- Нужно стремиться к выносу большинства классов в один файл. Можно оставлять в одном файле тесно связанные классы, которые друг без друга не используются, например, UseCase и DTO для этого UseCase.
- Весь код делится на слои. Нижние ничего не знают о верхних, верхние знают о нижних.
  Внизу слой app (приложение), над ним слой адаптеров, над ним - композит.

# App Layer
- Содержит в себе логику, обеспечивающую потребности бизнеса.
- Не должен содержать обращения к инфрастуктуре и другим системам. Вместо прямых обращений приложение должно объявлять абстрактный базовый класс и использовать его. Реализации абстрактного класса выносятся на слой адаптеров, и подставяются в конструкторы из слоя композитов.
- Каждое действие в приложении, возможное в системе, должно быть выражено как usecase - класс с публичным методом run.
- Параметры принимаются usecase в виде датаклассов или простых типов данных, их описание размещается в том же файле, что и usecase.
- Usecase-команда должен проводить валидацию полученных параметров при необходимости. Проверять нужно не структуру и типы данных, а значения и их семантику.
- Адаптеры, вызывающие usecase, должны проводить парсинг в правильную структуру ДО вызова usecase.
- Результат запроса возвращается в виде датаклассов или простых типов данных. Возвращаемые DTO описываются рядом в том же файле, и между разными usecase НЕ переиспользуются.
- Usecase отвечает за проверку прав при необходимости.

## App layer - Queries
- Usecase-запрос (Query) предназначен для выдачи данных из системы наружу. К таким классам не должно быть обращения из уровня приложения, только из адаптеров.
- Usecase-запросы группируются в пакете queries.
- Метод run должен быть идемпотентным.
- Usecase-запрос является абстрактным и не реализует выдачу данных. Реальное обращение к инфраструктуре должно быть в имплементации, имплементация размещается в адаптере к хранилищу.

## App layer - Commands
- Usecase-команда (Commmand) предназначен для изменения состояния системы (бизнес-объектов) по заложенным бизнес-правилам. К таким классам не должно быть обращения из уровня приложения, только из адаптеров.
- Usecase-команды группируются в пакете commands.
- Для доступа к хранилищу объявляет абстрактные базовые классы, имплементации размещаются в адаптерах.
- Рядом с командой в том же файле могут быть описаны дополнительные датаклассы, необходимые для работы UseCase.
- Пакет с командами может содержать в себе доменную модель. Подробнее ниже, в разделе Модель домена.

# Adapters
- Делится на 3 группы - interfaces, infrastructure и integrations.
- Вместо пакета adapters следует сразу создавать 3 указанных пакета, чтобы не плодить лишнюю вложенность.
- Адаптеры не должны иметь зависимостей друг от друга, только от приложения.
- Могут содержать файлы с настройками, выполненными с pydantic_settings.

## Adapters - interfaces
- Содержит модули, предоставляющие доступ другим системам к приложению.
- Отвечает за перевод из формата общения с другой системой в формат, доступный приложению.
- Здесь проводится парсинг из сырых данных в объекты для сценариев с помощью pydantic.TypeAdapters.
- Не содержит бизнес-логику, только обращается к usecase.

## Adapters - infrastructure
- Cодержит модули, предоставляющие приложению доступ к инфрастуктуре.
- Модули группируются по типу инфраструктуры (db, cache, file_storage и т.д.).
- Внутри пакета инфраструктурного типа имплементации базовых классов группируются по своему архетипу в app-слое (repos, queries, clients и т.д.).
- Здесь размещаются имплементации абстрактных классов из приложения.
- Может содержать в себе классы, обращающиеся к usecase.
- Проверять данные на структуру и типы в infrastrcuture не нужно, так как это внутренние объекты.

## Adapters - integrations
- Группа integrations содержит модули, обеспечивающие интеграцию с системами вне контура.
- Здесь размещаются имплементации абстрактных классов из приложения.
- Может содержать в себе классы, обращающиеся к usecase.
- Обязательно проверяет все данные, полученные от внешних систем с помощью Pydantic.
- Взаимодействие с внешней системой инкапулируется в класс-клиент
- Класс-клиент возвращает модели pydantic.
- Описание моделей размещается в модуле с клиентом и является описание контракта с внешней системой.

# Модель домена
- Содержит в себе классы, отражающие понятия из предметной области, и логику, связанную с этим понятиями.
- Состоит из объектов-значений, сущностей, инвариантов, агрегатов, критериев,  доменных usecase и доменных событий.
- Объекты-значения описываются датаклассами, зачастую с frozen=True. Такие объекты не имеют id, и являются подчиненными по отношению к сущностям. Может содержать логику, связанную с со своими данными, инварианты и критерии.
- Сущности описываются датаклассами, и всегда имеют идентификатор. Идентификатор может быть простым типом данных, кортежем простых данных, и даже объектом-значением. Может содержать логику, связанную со своими данными, инварианты и критерии.
- Агрегат - иерархия сущностей и объектов-значений, а так же логики, инвариантов и критериев. В корне иерархии всегда находится сущность. Агрегаты группируются в пакет aggregates.
- На каждый агрегат описывается свой класс-хранилище, умеющий извлекать/искать/сохранять конкретный вид агрегатов. ТОЛЬКО агрегаты имеют репозитории. В пределах модели домены данные можно извлекать только из хранилищ.
- Части агрегатов могут содержать ссылки на корни других агрегатов. Нельзя сослаться из одного агрегата на что-то внутри другого агрегата напрямую, только на корень.
- Инварианты - требования к сущности/агрегату. Описываются как criteria из classic-criteria. Также агрегат должен содержать инвариант, который проверит все остальные, чтобы можно было из любого места полностью проверить агрегат.
- Критериий - функции-предикаты, описывающие разные условия, в которых могут находиться объекты. Для реализации используется classic-criteria. Также используются для описания выборок при поиске в хранилищах.
- Агрегат извлекается из хранилища и сохраняется обратно всегда целиком, и всегда в одной транзакции, чтобы обеспечить целостность. При сохранении репозиторий ДОЛЖЕН убедиться, что все инварианты агрегата удовлетворены.
- Агрегаты не должны содержать логику управления другими агрегатами. При необходимости работы с несколькими разными агрегатами пишутся  доменные usecase.
- Доменные события - это события, происходящие во время работы usecase. Описываются с classic-signals. Обработчики (reaction) могут располагаться как в модели домена, если нужно запустить еще какое-то действие в домене, так и в адаптерах, если нужен вызов служебной логики. Обработчики события должны работать последовательно, без распараллеливания.

# Composite
- Здесь размещаются точки входа в приложение.
- Запускать точку входа препочтительно как модуль, например `python -m example.composite.api`
- Здесь находится инстанцирование нужных классов, передача инстансов друг другу для удовлетворения зависимостей. Каждый инстанс должен находиться в своем файле. В целом этот слой зачастую зеркалит структуру других слоев
