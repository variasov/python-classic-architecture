# Описание

В этом навыке описывается реализация "Классической" архитектуры в проекте на Python.
"Классическая" архитектура - смесь известных концепций, известных в сообществе:
- Чистая архитектура
- Domain Driven Design
- CQRS

Это центральный навык: он описывает, на какие слои делится приложение и как слои
связаны между собой. Правила каждого слоя описаны в отдельных навыках:

| Слой | Пакет | Навык |
|---|---|---|
| Приложение | `app/` | `python-classic-app` |
| Модель домена (часть app, опционально) | `app/commands/domain/` | `python-classic-domain` |
| Адаптер HTTP API | `interfaces/api/` | `python-classic-adapters-http-api` |
| Адаптер SQL DB | `infra/db/` | `python-classic-adapters-sql-db` |
| Композит | `composites/` | `python-classic-composite` |

Редко нужные подробности вынесены в файлы `references/` в каталоге навыка и читаются по необходимости:

| Файл | Когда читать |
|---|---|
| `references/tooling.md` этого навыка | Создание проекта, правка `pyproject.toml`, ошибки pyright/ruff/vulture |
| `references/testing.md` этого навыка | Написание тестов: организация `tests/`, подмена внешних систем, тесты клиентов integrations |
| `references/testing.md` навыка слоя | Написание тестов этого слоя |

# Когда использовать
- Когда пользователь запрашивает ревью кода или архитектуры.
- Во время разработки новых фич в Python-приложении.
- Перед работой с любым слоем: сначала этот навык, затем навык нужного слоя.

# Идея разделения на слои
- Весь код делится на слои. Нижние ничего не знают о верхних, верхние знают о нижних.
  Зависимости направлены только вниз.
  ```
  composites                         # собирает всё вместе, точки входа
      ↓
  interfaces | infra | integrations  # адаптеры, друг о друге не знают
      ↓
  app (commands, queries)            # бизнес-логика
      ↓
  domain (опционально)               # модель предметной области, ни от чего не зависит
  ```
- **app** - нижний, основной слой. Содержит логику, обеспечивающую потребности бизнеса,
  в виде usecase: команд (меняют состояние) и запросов (читают данные).
  Внутри команд может находиться модель домена (**domain**) - агрегаты, инварианты,
  критерии, абстрактные репозитории. Домен - нижележащий подслой app: остальной app знает
  о домене, домен не импортирует ничего из app. Домен опционален: он вводится, когда у предметной
  области есть объекты с собственными правилами.
- **adapters** - слой над app. Связывает приложение с внешним миром. Реализует
  абстрактные классы, объявленные в app, и вызывает usecase.
  Делится на 3 группы:
  - `interfaces` - доступ к приложению снаружи (HTTP API, чат-боты, планировщики, обработчики очередей);
  - `infra` - доступ приложения к своей инфраструктуре (БД, кэш, файловое хранилище);
  - `integrations` - доступ приложения к системам вне контура.
- **composite** - верхний слой. Инстанцирует классы всех слоёв, передаёт их друг
  другу через конструкторы, навешивает транзакции и аспекты, содержит точки входа.
- Приложение не обращается к инфраструктуре и другим системам напрямую. Вместо этого
  оно объявляет абстрактный базовый класс (ABC) и использует его. Реализация ABC
  размещается в адаптере и подставляется в конструктор в композите.

# Layout
- В корне проекта должен быть pyproject.toml.
- Приложение должно быть представлено namespaced Python-пакетом. Пакет должен лежать в `sources/`:
  ```toml
  [tool.setuptools.packages.find]
  where = ["sources"]
  namespaces = true
  ```
- Весь пакет состоит из namespace, ни одного файла __init__.py быть не должно.
- Все импорты должны быть абсолютными (от имени пакета) и размещаться в начале файла.
  ❌ `from .domain.loan import Loan`
  ✅ `from library.app.commands.domain.loan import Loan`
- Все классы принимают зависимости через конструктор.
- Нужно стремиться к выносу большинства классов в один файл. Можно оставлять в одном файле тесно связанные классы, которые друг без друга не используются, например, UseCase и DTO для этого UseCase.
- Тесты лежат в отдельном пакете `tests/` в корне проекта, а не внутри слоёв.

Типовая структура пакета:
```
sources/<package>/
  app/
    errors.py                  # AppError - базовый класс ошибок приложения
    clock.py                   # ABC Clock - источник текущего времени
    commands/
      domain/                  # агрегаты, ABC репозиториев, DomainError и доменные ошибки; не импортирует остальной app
      <system>.py              # ABC внешней системы, общий для нескольких команд
      use_cases/<group>/<usecase>.py
      signals.py               # контракты сигналов (при необходимости)
    queries/<group>/<query>.py # usecase-запросы, их DTO и ABC гейтвеев
  infra/
    db/                        # см. навык python-classic-adapters-sql-db
    clock/system.py            # SystemClock - реализация Clock на системных часах
  integrations/
    <system>/                  # клиенты к внешним системам
  interfaces/
    api/                       # см. навык python-classic-adapters-http-api
  composites/                  # см. навык python-classic-composite
tests/                         # см. references/testing.md
  unit/
  adapters/
  composites/
```

# Типизация и статический анализ
- Весь код, включая тесты, полностью типизирован: аннотированы аргументы и возвращаемые значения всех функций и методов, атрибуты классов, поля датаклассов. `Any` и `# type: ignore` не используются без крайней необходимости; если без них не обойтись, рядом пишется комментарий с причиной.
- Код проверяется тремя инструментами, все проверки должны проходить без ошибок:
  - **Pyright** в режиме `strict` - типы;
  - **ruff** с `select = ["ALL"]` - стиль и типичные ошибки;
  - **vulture** - неиспользуемый код.
- Эталонная конфигурация `pyproject.toml` (зависимости `dev`, pyright, ruff, vulture, pytest) - в `references/tooling.md`.
- Конфигурация общая для проекта. Новые исключения в `ignore` и `per-file-ignores` добавляются точечно, с комментарием о причине, и только когда правило противоречит архитектуре (например, имена, заданные спецификацией API). Отключать правило ради одного места нельзя - в таком месте пишется `# noqa: <код>` с причиной.
- Ложные срабатывания vulture (вызовы через фреймворки) подавляются белым списком `vulture_whitelist.py`, а не понижением `min_confidence`.

# Ошибки
Общие правила для ошибок всех слоёв. Базовые классы и размещение описаны в навыках слоёв: `AppError` - в `python-classic-app`, `DomainError` - в `python-classic-domain`.
- Ошибки - обычные исключения Python, сторонние библиотеки для ошибок не используются.
- Конкретные классы ошибок не содержат слова `Error` в имени: то, что это ошибка, видно по наследованию. Имя описывает ситуацию: `LoanNotFound`, `BookNotInCatalog`. Суффикс `Error` остаётся только у базовых классов (`AppError`, `DomainError`).
- Текст сообщения формируется f-строкой в `__str__`.
- Если у ошибки есть параметры, она оформляется датаклассом, параметры - его поля. Датакласс не делается `frozen`: при `raise` Python записывает в исключение `__traceback__`, и frozen-датакласс упадёт с `FrozenInstanceError`.
  ```python
  class ExtensionDaysNotPositive(DomainError):
      def __str__(self) -> str:
          return 'Срок продления должен быть положительным'


  @dataclass
  class LoanNotFound(DomainError):
      id: int

      def __str__(self) -> str:
          return f'Выдача с id={self.id} не найдена'


  raise LoanNotFound(id=loan_id)
  ```
- Адаптеры считают `AppError` и `DomainError` ожидаемыми ошибками и обрабатывают оба одинаково.

# Adapters
- Вместо пакета adapters следует сразу создавать 3 пакета `interfaces`, `infra`, `integrations`, чтобы не плодить лишнюю вложенность.
- Адаптеры не должны иметь зависимостей друг от друга, только от приложения.
- Могут содержать файлы с настройками, выполненными с pydantic_settings. Класс настроек описывается в адаптере (`settings.py`), а инстанцируется в композите.
- Для каждого типа адаптера есть свой навык. Если для нужного типа навыка нет, следуй общим правилам группы ниже.

## Adapters - interfaces
- Содержит модули, предоставляющие доступ другим системам к приложению: HTTP API, чат-боты, планировщики, обработчики очередей.
- Отвечает за перевод из формата общения с другой системой в формат, доступный приложению.
- Здесь сырые данные разбираются в датаклассы `Params` usecase, ДО вызова usecase. Инструмент разбора описан в навыке конкретного адаптера.
- Не содержит бизнес-логику и SQL, только обращается к usecase или испускает сигнал.
- Подписчик на сигнал, которому не нужна инфраструктура и который только вызывает usecase, - это interface: `interfaces/signals/<subscriber>.py`.

## Adapters - infra
- Cодержит модули, предоставляющие приложению доступ к инфрастуктуре.
- Модули группируются по типу инфраструктуры (db, cache, storage и т.д.).
- Внутри пакета инфраструктурного типа имплементации базовых классов группируются по своему архетипу в app-слое (repos, gateways, clients и т.д.).
- Здесь размещаются имплементации абстрактных классов из приложения.
- Здесь же размещаются подписчики на сигналы приложения, выполняющие служебную работу с инфраструктурой: `infra/<type>/subscribers/<subscriber>.py`.
- Может содержать в себе классы, обращающиеся к usecase (например, обработчики фоновых задач).
- Проверять данные на структуру и типы в infra не нужно, так как это внутренние объекты.
- Пока реальная реализация не готова, допускается заглушка (stub), реализующая тот же ABC и помеченная TODO.

## Adapters - integrations
- Группа integrations содержит модули, обеспечивающие интеграцию с системами вне контура.
- Здесь размещаются имплементации абстрактных классов из приложения.
- Может содержать в себе классы, обращающиеся к usecase.
- Обязательно проверяет все данные, полученные от внешних систем с помощью Pydantic.
- Взаимодействие с внешней системой инкапсулируется в класс-клиент.
- Класс-клиент работает с моделями pydantic. Описание моделей размещается в модуле с клиентом и является описанием контракта с внешней системой.
- Структура: `integrations/<system>/client.py` (модели и клиент), `settings.py`. Клиент сам реализует ABC из app и переводит модели pydantic в DTO app; отдельный класс-обёртка не нужен.
- Ответ «не найдено» внешней системы превращается в `None` или пустой результат, прочие ошибки HTTP и невалидный ответ - в исключение интеграции (свой класс, не `RuntimeError`).
- Тестирование клиента - в `references/testing.md`.

# Тестирование
Подробные правила вынесены в `references/testing.md`: общие - в этом навыке, правила уровня - в навыке слоя. Читай их, когда пишешь или правишь тесты.

## Пирамида тестирования
Слои архитектуры определяют пирамиду: каждый класс тестируется на уровне своего слоя, изолированно от остальных слоёв. Чем ниже уровень, тем больше тестов и тем они дешевле.
```
            /  композит  \          мало: собранное приложение,          -> python-classic-composite
           /    (e2e)     \         тестовая БД, stub-серверы
          /----------------\        внешних систем
         /     адаптеры     \       средне: каждый класс адаптера        -> python-classic-adapters-*
        /  (БД, HTTP, ...)   \      против своей технологии
       /----------------------\
      /       unit: app        \    много: usecase с in-memory fakes     -> python-classic-app
     /--------------------------\
    /        unit: domain        \  много: без фикстур и окружения       -> python-classic-domain
   /------------------------------\
```
- **Unit: domain** - агрегат собирается вручную, вызывается `check()`, метод или критерий. Ни БД, ни фикстур.
- **Unit: app** - usecase собирается с in-memory fakes репозиториев и гейтвеев и заглушками внешних систем, реализующими ABC из app. Проверяется логика usecase: валидация параметров (`__post_init__` датаклассов `Params`), оркестрация агрегатов, сигналы.
- **Адаптеры** - каждый класс адаптера проверяется против своей технологии, без остальных адаптеров:
  - infra - репозитории и гейтвеи на настоящей тестовой БД;
  - interfaces - ресурсы HTTP с фейковыми usecase;
  - integrations - клиенты против stub-сервера внешней системы.
  Строго говоря, это не unit-тесты (нужна БД или сеть), но тестируется один класс.
- **Композит** - интеграционный (e2e) тест собранного приложения. Композит импортируется как есть, с тестовым окружением: тестовая БД, адреса внешних систем указывают на stub-серверы. Проверяется сборка: маршруты подключены, транзакции и аспекты навешены, подписчики зарегистрированы, ошибки обрабатываются. Бизнес-сценарии повторно не перебираются: по одному-два сценария на usecase.

## Общие принципы
- Проверяется поведение, а не реализация: что вернул метод, что оказалось в хранилище, что ответил HTTP. Не проверяются количество SQL-запросов, порядок вызовов репозитория, факт и аргументы вызовов заглушек (исключение - фейковые usecase в тестах интерфейсов, где разбор запроса в параметры и есть проверяемое поведение), имена приватных полей. Тест должен падать только при изменении поведения, а не при рефакторинге внутри.
- Ошибки проверяются по типу, а не по тексту сообщения. Текст меняется, тип ошибки - контракт.
- Каждый уровень проверяет своё и не повторяет нижние: тест ресурса не перебирает бизнес-правила, тест композита не перебирает фильтры гейтвея.
- Своя инфраструктура (БД) не подменяется: в тестах адаптеров infra и композита используется настоящая тестовая БД. Боевая БД не используется никогда.

## Антипаттерны
- ❌ Импорт инстансов композита в unit-тестах и тестах адаптеров: им нужен собственный контролируемый инстанс. Импортировать композит можно только в тестах композита.
- ❌ Stubs и переключатели "тестового режима" в боевом коде.
- ❌ Один тест, проверяющий и домен, и HTTP, и БД. При падении непонятно, где ошибка.
- ❌ `pytest.raises(Exception)` без проверки типа: тест проходит и при неожиданной ошибке.
- ❌ Общая тестовая БД с ручной очисткой в порядке выполнения.

# Библиотеки
- `classic.criteria` - критерии (см. `python-classic-domain`).
- `classic.signals.Hub` - сигналы (см. `python-classic-app`, `python-classic-composite`).
- `classic.db_tools`, `classic.migrations` - работа с SQL DB (см. `python-classic-adapters-sql-db`).
- `classic.scheduler` - планировщик (см. `python-classic-composite`).
- `falcon`, `waitress` - HTTP API (см. `python-classic-adapters-http-api`).
- `pydantic`, `pydantic-settings` - парсинг в адаптерах и настройки.
- `pyright`, `ruff`, `vulture` - статический анализ (см. Типизация и статический анализ).
